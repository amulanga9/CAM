# CAM — оценка надёжности и масштабируемости

Дата ревью: 02.07.2026. Ветка: `claude/realestate-project-review-4i135x`.

## Что есть сейчас

Проект — два самодостаточных HTML-файла без сборки, бэкенда и зависимостей (кроме Leaflet и шрифтов с CDN):

| Файл | Размер | Что это |
|---|---|---|
| `index.html` | 444 КБ (18 155 строк) | Основной дашборд (тёмная тема): карта + карточки + модалка с сигналами риска. Данные — массив `const DATA` из 301 объекта, зашитый прямо в HTML (~16 000 строк из 18 000). |
| `cam_mvp.html` | 592 КБ | Ранний MVP (светлая тема) со **своей отдельной копией данных** (`RAW`, `G1`, `G3`). |

Важно понять: **базы данных в проекте пока нет**. От «мастер-файла» вы оторвались, но данные сейчас просто вшиты в код страницы как JSON-литерал. Это работает, но это не база — это следующая вещь, которую нужно оторвать.

## Оценка надёжности

**Что хорошо:**
- Схема данных строгая: у всех 301 записей одинаковые 52 поля, нет записей с «плавающей» структурой.
- Нет дублей `cam_id`, все координаты внутри Ташкента, нет логических противоречий (`is_overdue` ↔ `delay_days`, `blocks_done ≤ blocks_total`, `progress_pct` в пределах 0–100).
- Статика без бэкенда = нечему падать: страница либо открывается целиком, либо нет.

**Риски:**
1. **Две рассинхронизированные копии данных.** `index.html` и `cam_mvp.html` несут разные датасеты. Любое обновление нужно вносить дважды — рано или поздно они разойдутся (уже разошлись: в MVP 233 объекта, в основном — 301).
2. **Обновление данных = правка 16 000 строк внутри HTML.** Одна потерянная запятая — и вся страница молча умирает (белый экран без сообщения об ошибке).
3. **Зависимость от CDN** (unpkg, cdnjs, Google Fonts): при их недоступности ломается карта и типографика.
4. **Нет версионирования данных**: непонятно, от какой даты датасет, нельзя откатиться.

## Оценка масштабируемости

Текущий предел — примерно **1–2 тысячи объектов**: дальше HTML распухнет до мегабайт, парсинг и рендер начнут тормозить на телефонах. Но реальный барьер не технический, а процессный: **каждое обновление данных требует пересборки HTML руками**. Масштабируется не тот проект, где много данных, а тот, где данные обновляются без правки кода.

## Что сделано в этой ветке

1. **`data/objects.json`** — данные вынесены из HTML в отдельный файл. Это и есть первый настоящий шаг к базе: данные теперь обновляются заменой одного JSON, без правки кода. Рядом `data/objects.js` — фолбэк для открытия страницы двойным кликом (без сервера).
2. **`zhk.html`** — новая страница с карточками ЖК:
   - данные грузятся **динамически** из `data/objects.json` и перепроверяются каждые 60 секунд — обновили JSON, страница сама подхватила (индикатор «данные от …» в шапке);
   - в каждой карточке **слайдер из 4 слайдов**: оценка риска CAM → ход строительства → застройщик → цена и предложение; автопрокрутка каждые 5 с (останавливается при наведении), точки и стрелки;
   - поиск, фильтры по риску/классу/району, сортировки, живые счётчики в шапке;
   - показываются только 150 сопоставленных объектов (заглушки скрыты).

## Что дальше (дорожная карта)

1. **Ближайший шаг — уже сделан здесь**: данные в `data/objects.json`, страницы читают его. Переключите и `index.html` на этот же файл, а `cam_mvp.html` заархивируйте — источник данных должен быть один.
2. **Пайплайн обновления** вместо ручной правки: скрипт (Python/Node), который берёт реестр + domtut, валидирует (те же проверки, что в аудите выше), проставляет `updated_at` и кладёт готовый `objects.json`. Хостинг не меняется — GitHub Pages продолжает раздавать статику.
3. **Настоящая БД появляется тогда**, когда потребуется: поиск/фильтрация на сервере, личные кабинеты, история изменений оценки, объём >2–3 тыс. объектов. Разумный вариант для этой стадии — Supabase (PostgreSQL + готовое REST API + бесплатный тариф): фронтенд почти не меняется, `fetch` просто указывает на другой URL.
4. **Гигиена данных до любого масштабирования**: разобрать 36 групп дублей (ввести понятие «ЖК → очереди»), заполнить районы у 50 записей (можно автоматически по координатам), зафиксировать правило перевода `cam_score` в категорию риска.
